# Dijkstra 10 万节点压力测试报告

## 测试模型

测试直接使用 `route3d_dijkstra_planner` 的生产 Schema V2 加载器和 Dijkstra 核心，不是
用另一个简化算法估算。

| 项目 | 数值 |
| --- | ---: |
| 顶点 | 100,000 |
| 边 | 249,367 |
| 规则网格边 | 约 199,367 |
| 随机跨区捷径 | 50,000 |
| 捷径中的单向边比例 | 15% |
| 随机查询 | 20 次 |
| Schema | `route3d_topology / 2` 完整字段 |
| 随机种子 | `20260903` |
| CPU | Intel Core 7 240H，测试进程单核执行 |
| 内存 | 31 GiB |

复现命令：

```bash
cd /home/wei/github_code/topo_graph_m20_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 run route3d_dijkstra_planner dijkstra_stress_benchmark \
  --vertices 100000 \
  --shortcuts 50000 \
  --queries 20 \
  --seed 20260903
```

基准程序会在系统临时目录中生成完整 Schema V2 JSON，加载后执行查询，并自动删除临时
文件，不会向工作空间写入约 115 MiB 的测试图。

整个基准程序、生产加载器和 Dijkstra 搜索均为 C++17，并使用 `Release` 构建。

局部短路径。

## 结论

- 10 万点、约 25 万边时，当前 C++ Dijkstra 单次搜索为 0.40～47.01 ms，平均约
  27.88 ms；接近最坏情况时仍能在约 50 ms 内完成。
- 对“用户选择目标点后规划一次”以及路径失效时的事件驱动重规划，这个计算量完全可用。
- 纯搜索在本机能够覆盖 10 Hz 周期，但不建议把拓扑 Dijkstra 放进高频底盘控制循环；ROS
  消息、路径发布和 RViz 渲染还会产生额外开销，控制器应复用已规划路径。
- 启动阶段的主要成本是 115 MiB JSON 的解析：约 4.14 秒。图常驻后约 119 MiB，但通用
  JSON DOM 在解析/建图期间产生约 881 MiB 瞬时峰值。
- 典型自动骨架只有数百到数千点时，不会接近这个压力；当前 `regu_schema_v2` 的 109 点
  `1 → 109` 查询实测约 0.0127 ms。
- RViz 不应发布 10 万个文字 Marker。本版本已默认限制背景显示为 20,000 个点、50,000
  条边和 2,000 个标签；规划路径始终完整发布。

## 大规模工程建议

| 规模/需求 | 建议 |
| --- | --- |
| 小于 5,000 点、低频目标请求 | 当前 C++ Dijkstra 有充足余量 |
| 1 万到 5 万点、低频请求 | 直接使用，并保持图常驻，不要每次重新加载 JSON |
| 10 万点、偶发请求 | 当前实现可用；建议异步请求，超时阈值至少覆盖平台性能差异 |
| 10 万点、高频重规划 | 优先改为双向 Dijkstra 或带可采纳启发函数的 A*，并避免重复发布全图 Marker |
| 启动时间敏感 | 将 JSON 预转换为紧凑二进制图，或拆分静态几何与重复默认属性 |
| 内存敏感 | 不在每条边重复保存默认 metadata；加载时改为共享默认配置和紧凑数组 |

当前 ROS 节点只在启动时加载一次图，每次请求不会重复支付约 4.14 秒 JSON 加载时间。
